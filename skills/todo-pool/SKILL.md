# Todo Pool（openspec/todo.md 待办池）

`openspec/todo.md` 是项目级待办池（backlog）的单一文件。本 skill 是读写此文件的**单一事实源与操作入口**——条目格式、状态语义、落池动作、归档勾选动作都以本 skill 为准。

## 服务的主基调原则

**系统工程主基调第 4 条：开放的复杂巨系统。** todo 池是"想到了先记下来，别急着建 change"的候选层——候选池可以无限多、不占 WIP，活跃 change 才受 `constraints` 的 `references/wip-limit.md` 约束。这是"开放的复杂巨系统不能并行硬解"的工程化入口之一：把"想做的事"（候选层）与"正在做的事"（WIP）分层隔离，想做的事再多也不撑爆并发。

## 格式约定

### 文件结构

```markdown
# TODO（待办池）

项目级待办池。每条未勾选条目是一个潜在 change 的候选。

## 待办

- [ ] [P1] 支持暗色模式
- [ ] [P2] 优化首屏加载

## 进行中

- [ ] [P0] 重构支付模块
  - [ ] change: refactor-payments
  - [ ] change: refactor-checkout

## 已完成

- [x] [P1] 搭建 CI
  - [x] change: setup-ci
```

### 条目格式

主条目 + change 子项两级结构：

```markdown
- [ ] <优先级> <一句话结果>
  - [ ] change: <name>      ← 每个承接的 change 一个子项，缩进两空格
```

- **主条目**：`- [ ] <优先级> <一句话结果>`。优先级 `[P0]`（关键）/ `[P1]`（重要）/ `[P2]`（一般），可选，未标注视为 P2。`td-propose` 挑候选时按 P0 → P1 → P2 排序呈现。
- **写作约束**：主条目必须是**可验证的一句话结果**（如"支持暗色模式"），不是问题陈述或过程描述（如"优化性能"）。落池时按此约束改写。
- **change 子项**：`  - [ ] change: <name>`（缩进两空格），表示该 backlog 被某个 change 承接。`td-propose` 创建 change 时在该主条目下新增子项——一个 change 一个子项，可多 change 承接同一条。

### 规则

- **状态语义**：主条目 `- [ ]` = 未开始或进行中；主条目 `- [x]` = 已完成（全部 change 子项均已归档）。子项 `- [ ]` = 该 change 活跃；子项 `- [x]` = 该 change 已归档。
- **勾选时机**：只有 `td-archive` 在 change 归档成功后，走本 skill 的「勾选子项」子流程操作。其他 skill 不得勾选条目或子项。
- **追溯档案（子项永久保留）**：change 子项归档后**不移除**——它是"这条 backlog 最终被哪些 change 完成"的追溯档案；change 侧不写反向来源（保持单向），追溯就靠子项 + git log。
- **git 策略**：todo.md 是共享事实源，**必须提交**（不 ignore）。它是单文件，多人协作按**条目粒度人工协调**——同一时间只由一个人 propose / 勾选同一条目；不同条目互不冲突。
- **文件不存在**：视为空池，不主动创建。用户明确想记录 backlog 时才创建（走「落池条目」子流程；`td-propose` 挑候选时不创建）。
- **分节**：`## 待办` / `## 进行中` / `## 已完成` 是建议性组织，非强制——文件未分节时，按主条目/子项的 `- [ ]` / `- [x]` 状态语义处理即可。
- **不删条目**：完成的条目（含子项）保留在"已完成"节，作为 backlog 历史。删除只发生在用户明确要求时。

## 落池条目（可执行子流程）

**触发方**：`td-explore` 步骤 7（探索成果落池）、`td-system-audit` 步骤 5（审计问题落池）。调用方已征得用户同意 → 执行本子流程；用户拒绝 → 跳过，不触发本子流程。

**动作序列**：

1. 读 `openspec/todo.md`。
2. **文件不存在** → 询问用户"是否创建待办池文件？"（落池是新池的第一个候选）。用户同意 → 创建（带 `# TODO（待办池）` 头 + `## 待办` 节）；用户拒绝 → 放弃落池，跳过。
3. 写入一条主条目 `- [ ] <一句话结果>` 到**待办节**（`## 待办` 下；文件未分节 → 追加到文件末尾）。
   - 主条目按「格式约定」的**写作约束**改写。
   - 优先级 `[P0]/[P1]/[P2]` 可选标注，落池方未给时省略（未标注视为 P2）。
4. 落池完成。此条目是 backlog 候选，不占 WIP——后续 `td-propose` 从池里挑时承接。

**不勾选、不创建 change**——落池只写候选层，承接是 `td-propose` 的事。

## 勾选子项（可执行子流程）

**触发方**：`td-archive` 步骤 4（归档成功后）。只在 change 归档成功后执行。

**动作序列**：

1. 读 `openspec/todo.md`。
2. **文件不存在** → 跳过，不主动创建文件。
3. 查找含 `change: <name>` 子项的主条目（`name` = 本次归档的 change 名）。**找不到对应子项** → 跳过（该 change 不是从池里承接的）。
4. 勾选对应子项 `- [ ] change: <name>` → `- [x] change: <name>`。
5. 主条目勾选判定：主条目下**全部子项都已勾选** → 主条目勾选 `[x]`；**仍有子项未勾选** → 主条目保持 `- [ ]`（该 backlog 还有活跃 change）。
6. 子项**不移除**——保留为追溯档案（见「格式约定」的「追溯档案」条）。

**不触发「落池条目」、不新建条目**——勾选只更新既有条目的状态。

## 如何被引用

| skill | 读写动作 | 走本 skill 的哪个节 |
|---|---|---|
| `td-propose` | 步骤 3 读池挑候选（决策内联）；步骤 4 回写 change 子项（格式均查「格式约定」） | 格式约定 |
| `td-explore` | 步骤 7 探索成果落池（用户同意后） | 落池条目 |
| `td-system-audit` | 步骤 5 问题落池（用户同意后） | 落池条目 |
| `td-archive` | 步骤 4 归档成功后勾选对应 change 子项 | 勾选子项 |

单向关联：change 资产（proposal/design/tasks）**不得**出现对 `openspec/todo.md` 的引用——backlog 是候选层，change 资产是契约层，两层分层隔离（见 `td-propose` 的 Guardrails「提案不引用 TODO 池」）。
