# 人在回路

> 本文件与同目录的 `brooks-law.md` / `critical-buffer.md` / `delay-decision.md` / `wip-limit.md` / `yagni-ladder.md` 是平级兄弟文件，正文中出现的裸逻辑名均指同目录对应变体文件。

## 服务的主基调原则

**系统工程主基调第 2 条：总体设计部。** 巨系统里有些判断必须留给总体设计部，不能由分系统工程师（agent）自己决定。

**系统工程主基调第 3 条：综合集成。** 定性判断 + 数据 + 模型 → 反复迭代。人是定性判断的来源，机器是数据和模型的处理者，二者必须结合。

## 规则

### 必须停下来等用户拍板的场景

1. **公共契约变更**：API 形状、数据库 schema、配置文件格式、对外承诺的行为
2. **不可逆决策**（见同目录 `delay-decision.md`）
3. **生产环境影响**：部署、迁移、权限变更、数据修改
4. **超出当前 change scope 的影响**：改动会波及 change 之外的代码或系统
5. **agent 自己的置信度低**：agent 不确定方案是否对齐用户意图时
6. **WIP 硬约束 override**：由 `wip-limit` 的 override 流程触发（见同目录 `wip-limit.md` 的「硬约束 + override 机制」节第 4 步）。本文件在 override 回路里负责"描述风险 + 列选项 + 等用户确认"，回路编排由 `wip-limit` 单一持有。
7. **被 `/td-system-audit` 触发修复时**：audit 发现"局部最优但全局失调"或"agent 自己拍板了本应问用户的事"严重问题时，触发本文件——由总体设计部（用户）判断这是真全局失调还是可接受的局部优化。

### 强度叠加规则

以上第 1–5 类是**通用基线**，所有 profile × tier 下都生效——这是"必须停"的下限。

`field-assessment` 表 1 第 5 行定义各 tier 的 human-in-loop **额外触发条件**（tier 加成），表 2 定义各 profile 的**场景加成**——各加成的具体条件均以表 1、表 2 为准。

最终生效强度 = 第 1–5 类通用基线 **+** 表 1 tier 加成 **+** 表 2 profile 加成，三者叠加都生效，不替换。表 2 的 profile 加成与基线场景重叠时（如 brownfield"改老代码前"与基线第 4 类超 scope 场景、maintenance"生产环境改动前"与基线第 3 类），叠加只是强调，不矛盾。与其他位置表述冲突时，以表 2 为准。

**第 6、7 类的叠加语义**：第 6 类（WIP override）和第 7 类（audit 触发修复）是**特定流程的触发通道**，**不参与 profile × tier 叠加**——它们分别由 `wip-limit` override 流程和 `/td-system-audit` 触发，与 profile/tier 强度无关。但 override 流程里触发的 `brooks-law` / `critical-buffer` 评估，仍按当前 tier 强度执行。

### 不需要停下来的场景

**判定优先级：必停基线优先，直接推进是补集。** 本节仅适用于"未命中任何必停场景"的情形——第 1–5 类通用基线（+ 表 1 tier 加成 + 表 2 profile 加成）是**必须停的下限**，命中即停，**不因"无新信息"而跳过**。只有必停场景全部未命中、且本次没有新增关键决策点时，才适用本节直接推进。"无新信息"不是放行理由，是补集条件——放行的充分前提是：未命中必停基线 **且** 用户已授权继续 **且** 当前在已闭合决策框架内。

1. 可逆决策的"先用最简单方案往前走"
2. 在已闭合的设计框架内的实施细节
3. verification 步骤（除非失败且 agent 不知如何修复）

### 默认自主裁决（rulings, not stalls）

**默认姿态是推进，不是停下问。** 未命中必停基线时，agent 的第一反应应是**自己裁决并继续**，而不是停下来问用户——频繁停车比一次错误裁决代价更高（错误裁决的返工用户看得见、可回滚；停在问题上浪费用户一整天却什么也没买到）。

**只有四类 situations 才值得停下来问**（这是"必停基线"之外、从"该不该停"角度的收敛白名单；两者是叠加关系——命中基线必停，命中下列任一也停，其余一律自主裁决）：

1. **不可逆 / 破坏性操作**（one-way door，见同目录 `delay-decision.md` 的层次性）
2. **安全敏感操作**（凭证、鉴权、生产数据）
3. **worktree 之外的副作用**（merge / push 共享分支 / publish / 对外承诺）
4. **计划坏到每条路都是猜**（artifact 与现实冲突到无法自主选择，走「设计回写」通道）

其余一切冲突、歧义、计划缺陷——**自己裁，记进裁决账，继续走**。

### `Ruling:` 裁决记账（自主裁决的透明度补偿）

凡 agent 自主裁决（本可停下问、但按本节选择继续）的决策点，就地留一行裁决记录：

```
Ruling: <决定> — <为什么> — <错了的代价>
例：Ruling: 复用既有 retry helper 而非新建 — 仓库已有且语义匹配 — 若并发语义不符，重写为专用 helper 约半天
```

规则：

- 记录落在任务对应的验证证据附注或 tasks.md（与 checkpoint review 证据同处），让裁决在 artifact 里可见、可回溯
- `Ruling:` 是"我拍了板、理由在此、错了代价明确"的记账，**不是**免问令牌——命中必停基线或四类停止条件时，`Ruling:` 无效，必须停下问
- 与同目录 `delay-decision.md` 的 `td-cut:` / `yagni-ladder.md` 的 `shortcut:` 分工：`td-cut:` 标砍角、`shortcut:` 标走重路、`Ruling:` 标"本可问但我裁了"的决策点——三者都是代码/artifact 侧锚点，让机器的自主判断对总体设计部透明

## 触发时 agent 应做的事

本文件不靠 hook 强制，靠 agent 自觉识别场景；识别到后按以下步骤执行：

1. 描述当前状态："我正在做 X，遇到了 Y 决策点"
2. 列出选项 + 每个选项的影响
3. 给出 agent 的推荐 + 推荐理由
4. 明确等待："请决定，我等你回复再继续"

### 需用户回复的条目标号规则

呈现内容同时含**多个需要用户回复的章节**时（如报告里的"未解决的问题"与"建议的下一步"、探索总结里的"候选方向"与"建议的下一步"），各章节内条目的序列号**不得使用同一套编号**（如都从 1 开始）——用户回复"1"时，agent 无法判断对应哪个章节的哪个条目。改为**带章节前缀的编号**（如 `a1 / b1`），用户回复 `a2` 即明确对应第一个章节的第 2 条。

**标签必须带内容**：`a1` / `b1` 类标签只在其标注的条目内容**同时呈现**时成立。用户回复引用某标签时，若该标签条目内容已不在可见上下文，须重新内联该条目内容或改为文字重述（呈现纪律见 `system-engineering` 的「用户呈现纪律」节）。

## 不做的事

- 不对所有动作都"问一下"——那是过度打扰，不是人在回路
- 不在用户明确授权"自己往前走"后还反复停下来——用户授权过的范围，agent 自主推进

## 与其他 skill 的关系

- 与 `delay-decision` 配合：可逆决策延迟，但延迟期内触及不可逆点时，本文件触发
- 与 `brooks-law` 配合：用户考虑"加人手"时，brooks-law 提醒，本文件要求用户显式确认
- 与 `wip-limit` 配合：用户想并行硬解超过 wip-limit 上限的 change 时，wip-limit 硬阻塞，本文件在 override 流程里要求用户显式确认风险（第 6 类）。
