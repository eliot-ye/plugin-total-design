# 关键链缓冲保护

## 服务的主基调原则

**系统工程主基调第 1 条：系统工程。** 整体性能取决于瓶颈，不是平均值。
**系统工程主基调第 2 条：总体设计部。** 瓶颈识别必须站在系统全局立场，不能由分系统工程师各自判断。

这条规则来自 Goldratt 的约束理论（TOC）和关键链项目管理（CCPM）。但它的前提是钱学森系统工程——如果没有总体设计部视角，瓶颈识别就会变成"各分系统都觉得自己是瓶颈"的扯皮。

## 规则

### 识别关键链

在一个 change 的 tasks 序列里，关键链是**最长路径**——不是"任务最多"的路径，是"考虑资源约束后耗时最长"的路径。

### 保护缓冲

关键链末端的缓冲（project buffer）和支流汇入点的缓冲（feeding buffer）**不能被压缩**。

常见错误：
- "这个任务估计 2 小时，但实际上 1 小时就够了" → 压缩缓冲
- "我们可以并行做这几个任务" → 没识别资源冲突，假装有关键链外的并行路径
- "估计时打个 90% 的安全余量" → 余量被均匀分到每个任务，没有集中缓冲

## 触发时机

- 用户在 `/td-propose` 或 `/td-apply` 时，要求"加快进度"或"压缩估时"
- agent 自己生成 tasks.md 时
- 多个 change 在排队，用户想插队

## 触发时 agent 应做的事

1. 在 tasks.md 里显式标注关键链路径
2. 在关键链末端留 project buffer（默认总估时的 30–50%，按 tier 调整）
3. 拒绝把缓冲当"可压缩的余量"——它是系统吸收不确定性的容量
4. 当用户要求压缩时，先问："这是真瓶颈还是非瓶颈？非瓶颈压缩不影响整体性能。"

## 按 tier 调整

| tier | project buffer 比例 |
|---|---|
| `tier-small` | 20% |
| `tier-medium` | 35% |
| `tier-large` | 50% |

tier 越大，系统越复杂，不确定性越高，缓冲越厚。
