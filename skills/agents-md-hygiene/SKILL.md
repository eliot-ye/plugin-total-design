# Agent 指令文件卫生（AGENTS.md 编写规范）

用户项目根部的 agent 指令文件（AGENTS.md，各平台叫法不同，下称**主指令文件**）是每会话全量加载的常驻上下文。本 skill 是这类文件的**单一格式权威与操作入口**——体量、内容归属、拆分指针化、spec 联动规则都以本 skill 为准。

## 服务的主基调原则

**系统工程主基调第 1 条：系统工程。**

主指令文件是 agent 工作上下文的一个分系统，每条追加都是局部动作，必须从整体性能（常驻上下文的信噪比）反推。无判重的追加会让文件无限膨胀——指令稀释、条目互相矛盾、过时约定残留。本 skill 的体量上限与判重规则，约束的就是"再往主文件加一条"这个动作。

**系统工程主基调第 3 条：从定性到定量的综合集成。**

系统行为契约的唯一模型载体是 openspec 的 spec artifact。主指令文件一旦记载系统契约，就成了第二事实源，必然与 specs 漂移。本 skill 的 spec 联动规则约束"把系统契约写进主文件"这个动作：契约变更走 `td-propose` 落 specs，主文件只留指针。

## 格式约定

### 体量

- 主指令文件 **≤ 200 行**（启发值，非硬阈值；超限 → 触发「瘦身子流程」）
- 每条约定一条列表项或一小节，不展开长解释——解释放拆出文件

### 内容归属（写入前判定，三选一）

| 要写的内容 | 归属 | 动作 |
|---|---|---|
| 稳定工作方式：构建/测试/lint 命令、代码风格底线、安全红线 | 主指令文件 | 直接写入，一条一项 |
| 系统契约 / 行为事实：接口约定、不变量、对外行为 | `openspec/specs/` | 不写主文件，变更走 `td-propose`；项目无 openspec 结构 → 降级写入主文件，条目末尾标注 `<!-- 待 spec 化 -->` |
| 领域规则 / 领域细节 / 分平台变体 / 非总系统内容 | 拆出文件 | 主文件只留指针并说明应该什么时候读取 |

### 指针格式

```markdown
- <主题>：详见 `<相对路径>`，涉及该主题时读取
```

- 指针的语义是**按需读取**，不用平台级 import 语法（如 CLAUDE.md 的 `@path`）——那是无条件全量加载，等于把拆出的内容又常驻回去
- 拆出文件默认放 `docs/.agents/<topic>.md`（目录不存在则随首次拆分创建；项目已有惯用文档目录如 `docs/ai` 时从其惯例）。拆出文件内不再留指针链——需要再拆说明主题切分错了

### spec 联动

- 主指令文件与 `openspec/specs/` 冲突时，**以 specs 为准**：发现主文件条目与 specs 漂移 → 把该条目改为指针或删除；specs 反而缺失该契约 → 走 `td-propose` 补，不在主文件里修
- 主文件中带 `<!-- 待 spec 化 -->` 标注的降级条目，在项目引入 openspec 结构后迁移到 specs 并从主文件移除

## 增改子流程（每次写入主指令文件前执行）

**触发方**：agent 即将创建或修改用户项目的主指令文件时（含用户"记住这个约定"类请求）。

1. **判重**：通读现有条目，已有条目能覆盖新内容 → 原地更新该条，结束；没有 → 下一步。
2. **判归属**：按「内容归属」表三选一。
3. 归属主文件 → 写入；写入后文件将超 200 行 → 先走「瘦身子流程」腾出空间再写入。
4. 归属 specs → 走 `td-propose`（项目无 openspec 结构 → 按表的降级路径写入主文件）。
5. 归属拆出文件 → 创建或追加拆出文件，主文件写入指针。

## 瘦身子流程

**触发方**：用户要求整理/瘦身指令文件时；或「增改子流程」步骤 3 发现超限时。

1. 逐节过主文件，按「内容归属」表归类：稳定工作方式（留）/ 已是指针（留）/ 应迁出（拆出文件或转 specs）。
2. 输出迁移清单（迁出哪些节 → 落到哪些拆出文件、哪些应转 specs 指针），**等用户确认后**再动手。
3. 执行：迁出内容落到拆出文件（不删除内容），主文件重写为「稳定工作方式 + 指针清单」。
4. 收尾报告：迁出行数、主文件剩余行数、最终指针清单。

## Guardrails

- 判重先于追加——主文件膨胀的第一机制就是同一条约定被反复追加新副本
- 瘦身是重写操作，必须先给用户看迁移清单、确认后执行
- 迁出不删除内容；删除只发生在用户明确要求时
- 主指令文件是用户项目的共享文件：多人协作时按条目粒度协调，不自作主张回滚他人条目
