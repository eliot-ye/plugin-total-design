# Verification Before Completion

## 服务的主基调原则

**主基调第 3 条 + 第 1 条。** 动作：声明"完成"必须以定量证据（实跑验证命令的输出）支撑"系统行为符合契约"的定性结论——没有证据的完成声明是无根据的断言。第 6 节系统级验证是"总体性能≠各部分之和"的体现（局部绿不证明整合正确）；verification 是反馈控制回路的实时误差检测环节。

## 触发时机

- agent 即将声称"任务完成" / "bug 修复" / "测试通过" / "可以 commit 了"
- 任何"我搞定了"类的声明之前
- `td-apply` 步骤 4 里任务标记 `[x]` 之前
- `requesting-review` 给出"可以继续"之前

## 工作方式

### 1. 列出验证命令

对每个"完成"声明，先列出**具体的验证命令**——测试 / lint / build / type check 中该任务适用的全部，写出实际命令。

### 2. 实际跑这些命令

不是"我觉得会过"，是**实际执行**，拿到输出。

### 3. 检查输出

- 退出码是 0 吗？
- 输出里有 warning / error 吗？
- 测试覆盖了应该测的场景吗？

### 4. 给出 evidence-based 声明

错误声明："任务完成了。"
正确声明："任务完成。跑了 `pytest tests/test_auth.py`，12 个测试全绿。跑了 `mypy`，没 type error。"

### 5. 如果验证失败

**不要**：
- 立即"修一下"再跑——先理解为什么失败
- 声明"基本完成，就差这点"——要么完成，要么没完成
- 跳过失败的验证，先 commit——会把已知问题写进版本历史

**要**：
- 触发 `systematic-debugging` 走 4-phase 流程
- 如果修不了，触发 `constraints` 的 `references/human-in-loop.md` 停下来问用户

### 6. 系统级验证（跨分系统边界）

本节与 `td-apply` 步骤 6.2 的分工：**步骤 6.2 定义触发条件与 tier 分层强度，本节只定义执行层语义**。触发条件与 tier 分层强度一律以 `td-apply` 步骤 6.2 为准。在 `td-apply` 流程里，本节在步骤 6.1 change-level 验证通过之后触发；单独触发本 skill 时，若上游已有 change-level 验证产物，可直接进入本节。

change-level 验证通过 ≠ 系统整合正确。"总体性能不等于各部分性能之和"（论点归位与展开见本文档「服务的主基调原则」节）。跨分系统边界验证是它的执行层，执行时按下列三类验证覆盖受影响分系统之间的边界：

- 受影响分系统之间的接口/契约测试（集成边界，不是单测）
- 数据流跨分系统传递的正确性
- 边界 mock：一个分系统的行为变更是否破坏相邻分系统的契约

边界验证也走本 skill 的 1–5 节流程——列出验证命令、实跑、检查输出、evidence-based 声明、失败触发 `systematic-debugging`。

**验证不替代 change 级收尾 review**：本节两类验证（change-level + 系统级）全绿，只证明**实现符合已写下的断言**——它回答不了"断言本身写对了吗、实现与 design/spec 有无错配、有没有测试照抄实现 / 边界遗漏 / 契约漂移"。后者是 `requesting-review` 第 6 节 change 级收尾 review 的问题（review 对象是本 change 全部 diff，不是单个任务的绿测试）。在 `td-apply` 流程里这是 6.1→6.2→6.3 三步判定链：验证（6.1+6.2）通过 ≠ change done，还须走完 6.3 收尾 review 无 critical 才算 done。验证全绿后别急着宣布完成——那正是最容易被"我验证过了"的满足感骗过去、跳过收尾 review 的时刻。

## 常见合理化

| 合理化（agent 对自己说的话） | 现实 |
|---|---|
| "改完了，编译过了就算完成" | 编译通过只证明代码能跑起来，不证明行为符合契约——验证是行为证据，不是构建证据 |
| "这个改动很小，不用跑全量" | 完成声明的有效性不由改动体积决定——小改动破坏契约的方式和大改动一样多 |
| "测试之前是绿的，我没碰测试" | 代码变了，之前的绿就作废（见「之前测过」条）——重跑 |
| "就差最后一个边界，先标记完成" | 要么完成要么没完成，没有"基本完成"——差一个边界就是没完成 |
| "跑一遍太慢了，相信我" | 信任不能替代证据——慢测试正是最容易藏回归的地方 |
| "lint 只是风格问题，跳过" | lint 里的 type check / 未处理错误不是风格——按命令类别判断，不是按"风格"一刀切 |
| "这 3 个失败和我改的文件无因果——我只改了 A，失败全在 B/C" | 红灯不由"我碰没碰那个文件"裁定——全量跑出的失败默认算本 change 的，除非有新鲜基线证据（git stash 前后对照）证明它在我改动前就红 |
| "失败是存量 / pre-existing / 环境相关，与本次 change 无关" | "存量"是结论不是证据——判定存量必须拿出**本次改动前**的跑通记录；拿不出就当本 change 的红灯处理 |
| "测试全绿、过程中还修了几个 bug——验证都做完了，可以收工" | 验证做完了 ≠ 收尾 review 做过了。测试全绿只证明代码符合**你自己写的**断言；断言漏了边界、实现偏离 design 语义时照样全绿。修过 bug 是实现期点状自纠，不是对整体 diff 的系统性审读——收尾 review 不是"修过 bug"的副产品，仍须走 `requesting-review` 第 6 节 |

## 硬约束

### 不接受以下偷懒

- **"目测通过"**：UI 改动也要验证——snapshot test、E2E test、至少手动截图对比。"我看了一下觉得对"不是验证。
- **"应该没问题"**："我没改那块代码，应该没问题"——高频出错场景。跑全量测试，确认真的没问题。
- **"之前测过"**："这个测试我之前跑过"——代码变了，之前的测试结果就失效。重跑。
- **"红灯自行豁免"**：验证跑了、见到红灯，**不得用因果论证（"我没碰那文件"）或存量论证（"是 pre-existing"）自行豁免后宣布完成**。全量验证出的红灯默认算本 change 的；要判为无关，必须拿出**本次改动前的新鲜基线证据**（如 git stash 前后对照跑通），拿不出就当本 change 的红灯处理——触发 `systematic-debugging` 或上报用户裁决。这条管的是"跑了但洗白"，比"没跑验证"更隐蔽。
- **"park 掉自我怀疑"**：实施中一旦冒出"这个 panic / 这个边界会不会也和我的改动有关"之类的疑虑，**该疑虑本身即视为红灯**——必须当场验证或上报，不得记一句"以后再看"就继续标完成。压掉一个没验证的怀疑 = 埋一颗带病完成的雷。
